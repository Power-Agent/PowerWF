# Ground truth for the 200-task benchmark

This directory is evaluation data, not agent implementation and not UI content.
It is deliberately separate from `tasks/`, which contains only the sender's
initial natural-language message and public task metadata.

## Files

- `contract_oracles.jsonl` has exactly one `EpisodeGroundTruth` record for each
  `ep-001`–`ep-200`. Each record pins the source-message hash, ideal structured
  interpretation, canonical receiver-side instruction, required action types,
  decision rule, completion rule, and expected reviewer route.
- `contract_verification.jsonl` stores one programmatic verification record and
  semantic fingerprint per contract. It is separate so verification metadata
  cannot invalidate an otherwise unchanged physics implementation bundle.
- `manifest.json` records corpus hashes, counts, verification status, and the
  publication gate.
- `numeric_oracles/` contains final per-episode schedules and validated outcomes
  as they pass the frozen closed-loop workflow. Each file records input and
  artifact hashes, physical metrics, both natural-language completion messages,
  and its programmatic verification status.

The corpus currently distinguishes a *specified oracle* from a *verified
oracle*. Clarification tasks have deterministic contract outcomes: no physical
execution occurs and completion is 0%. Direct tasks specify the complete
execution contract, but their numerical optimum remains `pending` until the
frozen RC/dispatch optimization is validated with EnergyPlus and pandapower.
No placeholder number is treated as ground truth.

The standard workflow also runs a matched no-response nonlinear AC replay and
stores task-facing business metrics: feeder peak and rebound, voltage and
congestion violation areas, reserve capacity/duration/tracking, request-relative
renewable curtailment, and pay-as-bid settlement. Baseline-flexibility records
are generated by separate reduction and absorption validations; their lower
bound may be negative because the reported envelope is net demand at the BEM
grid interface and BEM-connected storage may export.

Use `experiments/run_numeric_oracle_batch.py` for resumable generation. It
routes baseline-flexibility tasks to the bidirectional workflow and refuses to
reuse evidence whose joint-dispatch configuration or physics-code bundle hash
is stale. The manifest is the authoritative count of currently verified
numeric oracles; `tasks/summary.json` mirrors that count and its contract hash,
and `validate_case.py` fails if they diverge.

Before reporting benchmark accuracy, every contract oracle must have a matching
`programmatically_verified` sidecar record and pass the independent
deterministic checks in `validate_case.py`: source hashes, schema
alignment, family-to-output mapping, direction-compatible windows, and defined
required outputs. Direct tasks also require a matching verified JSON record
under `numeric_oracles/`; every required numeric output must be non-null and
traceable to the frozen EnergyPlus/pandapower workflow. Programmatic verification
is not an expert-review claim. The application never
returns these private oracle records through `/api/episodes` or session APIs.

Regenerate the deterministic task and contract corpora with:

```powershell
.venv\Scripts\python.exe experiments\generate_episodes.py --reset-verified-physics
```

The reset flag is required once any numeric oracle is verified. Regeneration
retains a verified status only when every physical task field is unchanged;
changed contracts return to `pending` and require physics revalidation.

Then validate one-to-one IDs, source hashes, schemas, and publication status
with:

```powershell
.venv\Scripts\python.exe experiments\validate_case.py
```

Validation also checks each verified oracle's manifest hash, required business
outputs, two natural-language completion messages, acceptance/completion
consistency, and hashes of all stable physics inputs.
